# Repository candidate inventory

Research date: 2026-09-19. Initial language scope: **Python, TypeScript/JavaScript, Go, and Rust**.

This is a source-mining list, not the selected corpus. The [CVE shortlist](CVE_CORPUS_SHORTLIST.md) identifies individual issues worth examining next. No entry here implies an audited project, a validated benchmark label, or permission to redistribute its source.

It is also not an inventory of this repository's own code: the README's repository layout lists the modules, fixtures, scripts and run configurations ScanEval ships, and a scanner ScanEval evaluates, such as DeepSec, is a system in a run configuration rather than a corpus candidate.

The inventory contains 103 distinct source leads: 97 in the area tables and 6 runtime/developer-tool leads. Excluded and pending-maintenance entries are listed separately and are not included in that count.

## Scope and selection

- Count the language of the vulnerable implementation. A Python wrapper around a vulnerable C library does not create a Python SAST case. A TypeScript frontend does not bring a Java backend issue into scope.
- Include JavaScript with TypeScript for intake, but preserve the actual source language in each case. Keep framework, component role, and analysis span separately.
- Cover conventional applications, conventional automation, AI-assisted applications, and agentic workflows. Classify the evaluated operation, not the product's marketing category. "Production" describes deployment/use evidence, not a fifth workflow.
- Do not force equal language, severity, or CVE counts. Select distinct mechanisms and justified independent replication, then publish the remaining coverage gaps. Rust application logic and unsafe/native boundaries should be distinguishable.
- Java/JVM, C/C++, PHP, Ruby, .NET, and other languages are deferred. Linux and other systems projects remain useful future sources, but are not initial four-language cases.
- A broad repository pool is inexpensive to keep. The actual release should use fewer repositories with well-supported targets and controls. No optimal release size or final repository allocation has been established.

## How to read the evidence

A dated API push or commit establishes observed activity, not a security support guarantee. Check the supported release branch when selecting a snapshot.

"Named" means a primary project/vendor page identifies users or customers. It can cover a wider product family and does not prove use of the exact open-source edition. "Ecosystem dependency" means another product officially includes the component. "Vendor docs" or "production docs only" does **not** establish organizational adoption; those rows still need use evidence.

An actual CVE/GHSA or vendor bulletin is stronger than an advisory-index link. An empty GitHub advisory endpoint is not evidence of no CVEs. Index-only rows still need a concrete record, and reporting policies alone do not qualify. The tables retain these leads visibly instead of claiming that every row has passed admission.

Before promoting a row: establish current upstream/support status, public source for the relevant component, credible use evidence, an actual public security record, and a useful in-scope mechanism. Then validate the exact case under [the design's admission rules](DESIGN_DECISIONS.md#candidate-screening-and-disposition).
